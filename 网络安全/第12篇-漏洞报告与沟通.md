# 第 12 篇：漏洞报告与沟通——把洞变成"可交付的成果"

挖到漏洞只是完成了一半。厂商的安全团队每天收到几十份报告，能让他们**快速复现、认可影响、愿意修复**的，才是好报告。

这一篇讲四件事：

1. 报告怎么写；
2. 影响怎么量化；
3. 定级怎么沟通；
4. 被驳回/降级怎么办。

---

## 一、一份好报告的五个标准

| 标准 | 说明 |
| --- | --- |
| **可复现** | 按步骤操作，任何人都能复现 |
| **可验证** | 有请求/响应/截图，不是"可能存在" |
| **影响清楚** | 说清能读什么、改什么、影响多少用户/多少钱 |
| **边界干净** | 只用自己账号，敏感数据打码，不拖库 |
| **修复可落地** | 给出具体代码/配置建议，不是"请修复" |

**坏报告的特征：**

```text
标题：SQL 注入
内容：目标存在 SQL 注入，请修复。
证据：（无）
```

**好报告的特征：**

```text
标题：[高危] 订单查询接口存在水平越权，可读取任意用户订单
内容：前置条件 + 3 步复现 + 请求/响应 + 影响 + 修复建议
证据：Burp 请求、两张账号对比截图、curl 命令
```

---

## 二、报告结构

建议固定用这个模板：

```markdown
# [等级] 资产 + 漏洞类型 + 影响

## 一、漏洞概述
三到五句话说清：在哪、什么漏洞、能做什么、需要什么前提。

## 二、影响范围
域名/接口/版本/角色/受影响用户范围。

## 三、复现步骤
1. 注册账号 A、B
2. A 登录，访问 ...
3. 把参数 X 改成 B 的 ...
4. 返回 B 的数据

## 四、请求与响应
原始 HTTP 请求、关键响应片段、curl 命令。

## 五、影响评估
机密性/完整性/可用性、业务影响、是否需要登录、是否影响其他租户。

## 六、根因分析（可选）
哪一行代码/哪个配置导致。

## 七、修复建议
具体到代码/配置，给出正确写法。

## 八、参考资料
CVE、OWASP、官方文档。
```

### 1. 标题

公式：

```text
[等级] 资产/功能 + 漏洞类型 + 影响
```

例子：

```text
[高危] 订单详情接口水平越权，可读取任意用户订单
[高危] 头像上传功能可上传 PHP 文件并执行
[中危] 搜索接口反射型 XSS，可窃取用户 Cookie
[中危] 密码找回 token 可预测，可重置任意账号
[低危] 登录接口缺少频率限制，可被撞库
```

不要：

```text
SQL 注入
一个漏洞
某站存在安全问题
```

标题要让厂商一眼知道"值不值得优先看"。

### 2. 概述

```markdown
## 一、漏洞概述

`GET /api/order/{id}` 只校验用户是否登录，没有校验订单归属。
攻击者登录后修改 `id`，可读取其他用户的订单详情，包括收货地址、手机号、商品金额。
无需特殊权限，普通用户即可利用。
```

要点：

- 接口/功能写清楚；
- 漏洞类型写清楚；
- 影响写清楚；
- 前置条件写清楚。

### 3. 复现步骤

````markdown
## 三、复现步骤

1. 注册两个账号：`alice@example.com`（A）、`bob@example.com`（B）。
2. 用 B 创建一个订单，记下订单 ID `1002`。
3. 用 A 登录，获取 A 的 Cookie。
4. 发送以下请求：

```http
GET /api/order/1002 HTTP/1.1
Host: shop.example.com
Cookie: session=<A 的 session>
```

5. 响应返回 B 的订单信息，包含 `receiver`、`phone`、`address`。
6. 把 `1002` 改成 `1001`，返回 A 的订单，确认接口本身正常。
````

要求：

- 步骤编号；
- 账号是自己注册的；
- 请求可直接复制；
- 关键响应片段贴出来；
- 截图带 URL 和账号。

### 4. 证据

- Burp 请求/响应原文；
- 两个账号的对比截图；
- `curl` 命令（方便厂商复现）；
- 复杂流程录屏；
- 敏感字段打码。

```bash
curl -s 'https://shop.example.com/api/order/1002' \
  -H 'Cookie: session=<REDACTED>'
```

**不要**把真实用户的姓名、手机号、地址贴进报告。用自己两个账号的数据，或者打码。

### 5. 影响

不要只写"可读取数据"，要写：

```markdown
## 五、影响评估

- 可读取任意用户的订单详情：收货人、手机号、地址、商品、金额；
- 普通用户即可利用，无需管理员权限；
- 订单 ID 为递增数字，可批量遍历；
- 影响范围：所有注册用户；
- 风险：用户隐私泄露、精准诈骗、竞品情报。
```

如果有数量，给一个**保守估计**：

```text
按订单 ID 递增估算，当前日订单量约 1 万，历史订单可遍历。
```

不要为了显得严重而夸大，厂商会验证。

### 6. 根因

````markdown
## 六、根因分析

`OrderController.detail()` 只做了登录校验：

```java
Order order = orderService.getById(id);
return order;
```

缺少归属校验：

```java
if (!order.getUserId().equals(currentUser.getId())) {
    throw new ForbiddenException();
}
```
````

根因分析能体现你读懂了代码，也能帮厂商快速定位。

### 7. 修复建议

要具体：

````markdown
## 七、修复建议

1. 在详情、导出、下载、编辑等所有对象级接口增加归属校验：

```java
Order order = orderService.getById(id);
if (order == null || !order.getUserId().equals(currentUser.getId())) {
    throw new NotFoundException();
}
```

2. 不要返回 403 区分"存在但无权限"，统一返回 404，避免泄露对象存在性。
3. 对订单 ID 使用不可枚举的 UUID/雪花 ID，作为纵深防御。
4. 增加越权访问的审计日志和告警。
````

不要写"请开发修复"，要写"改哪里、怎么改"。

## 八、定级：别只看漏洞类型

厂商定级通常看四个维度：

```text
前提条件 × 影响范围 × 数据敏感度 × 利用难度
```

同样是 IDOR：

- 读自己的订单和读别人的订单，等级不同；
- 读昵称和读身份证/银行卡，等级不同；
- 需要管理员权限和普通用户即可，等级不同；
- 只能读一条和能批量遍历，等级不同。

### 常见定级参考

| 漏洞 | 前提 | 典型等级 |
| --- | --- | --- |
| 未授权 RCE | 无 | 严重/高危 |
| 登录后 RCE | 普通用户 | 高危 |
| SQL 注入（可拖库） | 无/普通用户 | 高危 |
| SSRF（可读云凭证） | 无/普通用户 | 高危 |
| 水平越权（敏感数据） | 普通用户 | 高危 |
| 水平越权（低敏感） | 普通用户 | 中危 |
| 存储型 XSS（管理员可见） | 普通用户 | 高危 |
| 反射型 XSS | 需诱导点击 | 中危 |
| CSRF（管理员操作） | 需管理员访问 | 中危/高危 |
| 开放重定向 | 无 | 低危 |
| 信息泄露（版本号） | 无 | 低危/信息 |
| 缺少限流 | 无 | 低危 |

### CVSS 3.1

报告里可以附 CVSS 向量，方便厂商对齐：

```text
CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N   # 越权读敏感数据，约 6.5
CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H   # 未授权 RCE，9.8
```

但 CVSS 不衡量业务影响。一个"中危"的越权，如果涉及百万用户住址，业务影响可能比一个"高危"的测试环境 RCE 更大。**用业务语言补充。**

## 九、和厂商沟通

### 首次提交

```text
标题：...
概述：...
复现：...
证据：...
影响：...
修复：...
```

不要：

- 一上来就要求"给多少钱"；
- 用威胁语气；
- 附一堆无关的扫描报告；
- 把漏洞发到公开群/社交媒体。

### 跟进

- 一般 3–5 个工作日后再问；
- 提供报告编号；
- 问"是否需要补充材料"，而不是"为什么不修"；
- 紧急漏洞（RCE、大量数据泄露）可以说明紧急性，但不要骚扰。

### 厂商说"复现不了"

按顺序排查：

1. 环境差异：版本、角色、租户、区域；
2. 请求差异：Header、Cookie、Content-Type、编码；
3. 前置条件：是否需要先创建某个对象；
4. WAF/缓存：换 IP、换参数、清缓存；
5. 提供 `curl` 和录屏；
6. 请厂商给测试账号/环境，你复现给他们看。

### 厂商降级

不要吵，拿证据：

```text
这个接口返回的字段包括：姓名、手机号、收货地址、订单金额。
订单 ID 为递增，普通用户即可遍历。
按当前日订单量估算，影响范围是所有历史订单。
请问定级是否考虑了这些数据字段和批量性？
```

如果厂商仍坚持，接受或走平台申诉；不要威胁公开。

### 重复

- 接受重复，问清楚"原报告覆盖的范围"；
- 如果你的入口/参数/角色不同，说明差异；
- 不要换个 URL 重复提交同一问题；
- 把精力放在新面。

### 披露

- 遵守平台/厂商的披露政策；
- 修复前不公开细节；
- 修复后如需 writeup，删掉敏感数据和可直接利用的 payload；
- 不发布真实用户数据。

## 十、被驳回/降级怎么办

| 理由 | 应对 |
| --- | --- |
| 超出范围 | 确认 scope，停止测试 |
| 重复 | 接受，找变体或新目标 |
| 无法复现 | 补 curl/录屏/环境说明 |
| 无实际影响 | 补影响链；如果确实无影响，接受 |
| 已知问题 | 查补丁，找绕过/新入口 |
| 风险接受 | 请厂商书面确认；按政策处理 |
| 证据不足 | 补请求/响应/截图 |
| 扫描器误报 | 手工复现，去掉误报 |

**判断"是否值得申诉"：**

- 你有明确的、可复现的影响；
- 厂商的定级标准与你的证据不匹配；
- 你愿意提供更多材料。

如果只是"觉得应该更高"，没有新证据，申诉通常没用。

## 十一、提交前检查清单

- [ ] 标题包含资产、漏洞类型、影响。
- [ ] 概述能在 5 句话内说清。
- [ ] 复现步骤编号，账号是自己注册的。
- [ ] 请求/响应原文完整，敏感值打码。
- [ ] 有 `curl` 或录屏，厂商能独立复现。
- [ ] 影响写到数据字段/用户范围/业务后果。
- [ ] 修复建议具体到代码/配置。
- [ ] 没有真实用户数据、没有 webshell、没有拖库。
- [ ] 没有超出 scope 的测试。
- [ ] 查过公开报告，确认不是已知重复。
- [ ] 附件命名清楚，截图带 URL/时间。
- [ ] 语气客观，没有威胁/夸大。


真正拉开差距的，不是"会多少 payload"，而是：

1. **能看懂业务**，知道哪里可能出错；
2. **能控制边界**，只证明、不破坏；
3. **能写清楚**，让厂商愿意修；
4. **能持续复盘**，把一次漏洞变成一套方法。

最后一篇是速查手册，把常用命令、payload、检查表集中在一起，方便实战时翻。
