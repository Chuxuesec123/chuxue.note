# 第 10 篇：逻辑漏洞与越权——扫描器看不见的地方

前面九篇大多是"技术漏洞"：输入拼接、反序列化、组件版本。这一篇是"业务漏洞"：

- **越权**：该看 A 的数据，你看到了 B 的；该是普通用户，你成了管理员。
- **逻辑漏洞**：价格、数量、优惠券、验证码、找回密码、并发，业务流程没想清楚。

这类洞**扫描器基本扫不出来**，但 SRC 里占比很高，因为你只需要两个账号和一台 Burp。

---

## 一、越权的三种类型

### 1. 水平越权（IDOR）

同级用户之间互相访问。典型接口：

```http
GET /api/order/1001 HTTP/1.1
Host: target.com
Cookie: session=alice
```

把 `1001` 改成 `1002`，如果返回了 Bob 的订单，就是水平越权（Insecure Direct Object Reference）。

常见参数：

```text
user_id、uid、order_id、address_id、file_id、invoice_id
account、phone、email、id、no、uuid
```

### 2. 垂直越权

低权限用户执行高权限操作：

```http
POST /admin/user/delete HTTP/1.1
Cookie: session=normal_user
```

如果普通用户能调通管理员接口，就是垂直越权。常见于：

- 前端隐藏了按钮，但后端没校验角色；
- 只校验"是否登录"，不校验"是否管理员"；
- 管理员接口路径可猜：`/admin`、`/api/admin`、`/manage`；
- 旧版本 API 没加权限：`/api/v1/admin`。

### 3. 未授权访问

根本不需要登录：

```bash
curl http://target/api/user/list
```

如果直接返回用户列表，就是未授权。常见于：

- 内部接口暴露在公网；
- Swagger/Actuator 没关；
- 静态资源目录可列；
- 测试环境没鉴权。

## 二、IDOR 本地实验

一个最小 Flask 靶场：

```python
from flask import Flask, request, jsonify

app = Flask(__name__)

ORDERS = {
    1: {"id": 1, "user": "alice", "item": "book", "price": 30},
    2: {"id": 2, "user": "bob", "item": "phone", "price": 3000},
}

@app.route("/api/order/<int:oid>")
def order(oid):
    user = request.headers.get("X-User")
    if not user:
        return {"error": "login required"}, 401
    o = ORDERS.get(oid)
    if not o:
        return {"error": "not found"}, 404
    # 漏洞：只检查登录，没检查订单归属
    return jsonify(o)

if __name__ == "__main__":
    app.run(port=9100, debug=True)
```

启动：

```bash
python3 idor_lab.py
```

Alice 访问自己的订单：

```bash
curl -H 'X-User: alice' http://127.0.0.1:9100/api/order/1
```

Alice 访问 Bob 的订单：

```bash
curl -H 'X-User: alice' http://127.0.0.1:9100/api/order/2
```

如果返回 `"user": "bob"`，说明水平越权成立。

修复：

```python
if o["user"] != user:
    return {"error": "not found"}, 404
```

**注意：** 未授权时返回 404 而不是 403，可以避免泄露"这个订单存在"。

### ID 不是数字也没关系

```text
/api/invoice/8f14e45fceea167a5a36dedd4bea2543
```

UUID/哈希 ID 只是"难猜"，如果它出现在分享链接、邮件、日志、前端 JS 里，一样能越权。**不要以为用了 UUID 就安全。**

### GraphQL 的 IDOR

```graphql
query {
  node(id: "VXNlcjoy") {
    ... on User {
      email
      phone
    }
  }
}
```

`node(id:)` 里的 Base64 只是 `User:2`。GraphQL 常见问题：

- introspection 没关，直接看 schema；
- 每个 resolver 没做对象级权限；
- 批量查询绕过限流。

## 三、批量赋值（Mass Assignment）

后端把请求 JSON 直接绑到用户对象：

```python
@app.route("/api/profile", methods=["POST"])
def update_profile():
    user = USERS[request.headers["X-User"]]
    user.update(request.json)   # 漏洞：什么字段都收
    return jsonify(user)
```

正常请求：

```json
{"nickname": "alice"}
```

攻击者加字段：

```json
{"nickname": "alice", "is_admin": true, "balance": 999999}
```

如果 `is_admin`、`balance` 被写进对象，就是批量赋值/参数覆盖。

常见敏感字段：

```text
is_admin、role、roles、permissions、status、verified
balance、points、vip_level、price、amount
user_id、tenant_id、company_id
```

修复：

```python
allowed = {"nickname", "avatar"}
data = {k: v for k, v in request.json.items() if k in allowed}
user.update(data)
```

或者用 DTO/白名单显式赋值。

## 四、JWT：别自己发明鉴权

JWT 结构：

```text
header.payload.signature
```

三段都是 Base64URL。header：

```json
{"alg":"HS256","typ":"JWT"}
```

payload：

```json
{"sub":"alice","role":"user","exp":1700000000}
```

### 常见问题

| 问题 | 测试 | 风险 |
| --- | --- | --- |
| `alg: none` | 改 header 为 `{"alg":"none"}`，去掉签名 | 某些库接受无签名 token |
| 弱密钥 | 用 hashcat 跑字典 | 可伪造任意用户 |
| 算法混淆 | RS256 公钥当 HS256 密钥 | 可伪造 |
| `kid` 注入 | `"kid":"../../../../dev/null"` | 路径穿越/空密钥 |
| `jku`/`x5u` | 指向攻击者 JWKS | 服务端拉取恶意公钥 |
| 不校验 `exp` | 用过期 token | 会话永不过期 |
| 不校验 `aud`/`iss` | 拿其他系统 token | 跨系统冒用 |

### `alg:none` 测试

原始 token：

```text
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJhbGljZSJ9.xxx
```

改成：

```text
eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJzdWIiOiJhbGljZSIsInJvbGUiOiJhZG1pbiJ9.
```

注意最后还有一个点，签名段为空。很多现代库默认拒绝 `none`，但老系统/自写解析器可能中招。

### 弱密钥

```bash
hashcat -m 16500 jwt.txt rockyou.txt
```

`16500` 是 JWT HS256 的模式。跑出来就能自己签任意 payload。

### 算法混淆

服务端用 RS256 公钥验签，但代码允许 `alg` 由 token 决定。攻击者把 `alg` 改成 `HS256`，用**公钥**作为 HMAC 密钥签名。服务端用公钥验 HMAC，结果通过。

修复：**服务端固定算法**，不要相信 token 里的 `alg`。

### 正确写法（PyJWT）

```python
import jwt

payload = jwt.decode(
    token,
    public_key,
    algorithms=["RS256"],   # 固定，不要用 token 里的 alg
    audience="my-api",
    issuer="https://auth.example.com",
)
```

不要：

```python
jwt.decode(token, options={"verify_signature": False})  # 等于没验
```

## 五、支付与金额：最值钱也最危险

支付逻辑漏洞的测试**必须在沙箱/本地**，不要对生产真实下单、真实退款。

### 1. 价格篡改

```http
POST /api/order HTTP/1.1
Content-Type: application/json

{"product_id": 1, "quantity": 1, "price": 0.01}
```

如果服务端直接用客户端传来的 `price` 计算，就能一分钱买。

修复：**价格从数据库查，永远不信客户端。**

### 2. 数量/金额为负

```json
{"quantity": -1, "price": 100}
```

总价变成 `-100`，可能让余额增加，或者退款金额变大。

### 3. 优惠券

- 同一个券重复使用；
- 多个券叠加；
- 改 `coupon_id` 用别人的券；
- 改 `discount` 金额；
- 过期券改时间；
- 退款后券退回，再次使用。

### 4. 支付回调伪造

```http
POST /pay/notify HTTP/1.1

order_id=1001&status=SUCCESS&sign=...
```

如果回调不验签，攻击者直接发 `status=SUCCESS`，订单变已支付。

修复：

- 校验签名（RSA/HMAC）；
- 校验订单金额、商户号；
- 幂等处理，防重复回调；
- 服务端主动查支付网关，不只信回调。

### 5. 整数溢出/精度

```json
{"amount": 0.1, "quantity": 3}
```

浮点精度可能导致 `0.30000000000000004`，或者四舍五入后少付。金额用**整数分**存储和计算。

## 六、验证码、登录与找回密码

### 验证码

| 问题 | 怎么测 |
| --- | --- |
| 可重复使用 | 同一个验证码提交两次，第二次仍成功 |
| 不校验 | 删除 `captcha` 参数，或传空值 |
| 验证码在响应里 | 看接口返回 JSON 有没有 `code` |
| 无过期时间 | 10 分钟后再用 |
| 无次数限制 | 连续错误 100 次不被锁 |
| 与手机号不绑定 | A 的验证码用于 B 的手机号 |
| 前端校验 | 禁用 JS / 直接请求接口 |

短信验证码还要看：

- 4 位/6 位，是否有尝试次数限制；
- 验证成功后是否立即失效；
- 是否返回在响应里；
- 是否可以修改 `phone` 参数给任意号码发短信（短信轰炸）。

**不要对真实目标做短信轰炸**，只用自己的手机号测一两次。

### 登录

- **用户枚举**：不存在用户返回"用户不存在"，存在用户返回"密码错误"；或者响应时间不同。
- **无锁定**：连续失败不锁，可以撞库。真实目标不要跑大字典。
- **默认口令**：`admin/admin`、`test/test`，只试一两次。
- **2FA 绕过**：
  - 直接访问登录后的 URL，跳过 2FA；
  - 把 `verify=false` 改成 `true`；
  - 验证码可复用；
  - 备份码无次数限制。

### 找回密码

```http
POST /api/reset/send HTTP/1.1
Content-Type: application/json

{"email":"victim@example.com"}
```

常见问题：

1. **重置 token 可预测**：`MD5(email)`、`base64(email)`、时间戳、递增 ID；
2. **token 不绑定用户**：拿到自己的 token，改 `email` 参数重置别人；
3. **token 不过期/可复用**：用一次后还能用；
4. **token 泄露在响应里**：接口直接返回 `reset_token`；
5. **Host 头投毒**：

```http
POST /reset HTTP/1.1
Host: attacker.example

email=victim@example.com
```

如果应用用 `Host` 拼重置链接，邮件里的链接会指向攻击者域名，token 就到手了。

6. **邮件轰炸**：无频率限制，反复发送。

**测试边界：** 只用自己的邮箱/账号；不要给真实用户发重置邮件，不要猜别人的 token。

## 七、并发与竞态：一次只能成功，但你发了 20 次

典型场景：

- 优惠券只能领一次，并发领 20 次；
- 余额 100，同时发起 2 笔 100 的提现；
- 库存 1，同时下 10 单；
- 积分兑换，同一积分扣多次；
- 退款，同一订单退多次。

### Python 并发脚本

```python
import threading
import requests

URL = "http://127.0.0.1:9200/api/coupon/redeem"
COOKIE = {"session": "alice"}
BARRIER = threading.Barrier(20)
RESULTS = []

def redeem():
    BARRIER.wait()  # 让 20 个线程尽量同时发
    r = requests.post(URL, cookies=COOKIE, json={"coupon": "NEW2024"})
    RESULTS.append(r.text)

threads = [threading.Thread(target=redeem) for _ in range(20)]
for t in threads:
    t.start()
for t in threads:
    t.join()

print(RESULTS)
```

如果成功次数 > 1，说明存在竞态。

### 更快的打法

- Burp Suite 的 **Turbo Intruder**；
- HTTP/2 的 **Single Packet Attack**：把多个请求放在同一个 TCP 包/同一毫秒发出，绕过网络抖动；
- 本地用 `ab`、`wrk` 做压力测试。

### 防御

```sql
-- 原子扣减，影响行数为 0 就失败
UPDATE coupon
SET used = 1
WHERE id = ? AND used = 0;
```

- 数据库唯一约束（一个用户一张券）；
- 事务 + 行锁 `SELECT ... FOR UPDATE`；
- 幂等键（idempotency key）；
- 分布式锁（Redis `SET NX`）；
- 不要"先查再改"，要"原子更新"。

## 八、其他常见业务漏洞

### 注册/账号

- 重复注册覆盖已有用户；
- 注册时批量赋值 `role=admin`；
- 邀请码/推荐人可篡改，刷奖励；
- 邮箱/手机绑定不验证；
- 改密码不需要旧密码。

### 订单/退款

- 已发货订单还能取消；
- 已使用服务还能退款；
- 退款金额可改；
- 退款后优惠券退回，再次使用；
- 订单状态机跳步：`待支付 → 已完成`。

### 接口绕过

- 旧版本 API 没鉴权：`/api/v1/admin`；
- 换 HTTP 方法：`GET /admin` 403，`POST /admin` 200；
- `X-HTTP-Method-Override: PUT`；
- 路径规范化：`/admin/..;/`、`/%2e/admin`、`/admin%2f`；
- 大小写：`/Admin`、`/ADMIN`；
- 后缀：`/admin.json`、`/admin/`。

### Host 头

- 密码重置链接投毒；
- 缓存投毒；
- SSRF；
- 访问内网虚拟主机。

只在授权范围测，不要污染真实缓存。

## 九、防御：把"信任"收回来

### 1. 每个请求都做对象级鉴权

```python
order = Order.query.get(order_id)
if order is None or order.user_id != current_user.id:
    abort(404)
```

不要只在列表页过滤，详情页、导出、下载、编辑都要查。

### 2. 默认拒绝

```python
@app.before_request
def require_login():
    if request.endpoint not in ("login", "register", "static"):
        if not current_user:
            abort(401)
```

管理员接口再加角色校验，不要靠前端隐藏。

### 3. 字段白名单

```python
ALLOWED = {"nickname", "avatar"}
data = {k: v for k, v in request.json.items() if k in ALLOWED}
```

### 4. 金额服务端计算

```python
product = Product.query.get(product_id)
total = product.price * quantity   # 不读客户端 price
```

### 5. 幂等与事务

- 支付回调带唯一 `transaction_id`，重复回调直接返回成功；
- 扣库存/扣余额用原子 SQL；
- 关键操作记录审计日志。

### 6. 限流与验证码

- 登录、短信、找回密码按 IP + 账号限流；
- 验证码一次性、5 分钟过期、错误 5 次失效；
- 敏感操作二次验证。

### 7. JWT

- 强随机密钥，定期轮换；
- 固定算法，拒绝 `none`；
- 校验 `exp`、`aud`、`iss`；
- 不要把敏感信息放 payload（只是 Base64，不是加密）。

## 十、SRC 里怎么测

1. **准备两个账号**：A（普通用户）、B（另一个普通用户），有条件再准备管理员。
2. **抓 A 的请求**，把 Cookie/Token 换成 B 的，或把资源 ID 换成 B 的，看能否访问。
3. **用 Autorize 插件**：它自动用低权限 Cookie 重放，标红相似响应；但误报多，必须手工确认。
4. **不要碰真实用户数据**：用自己注册的两个账号互测；如果 ID 遍历到真实用户，立即停止，不要下载/传播。
5. **支付只测沙箱**：不要真实下单、不要真实退款、不要伪造真实回调。
6. **报告写清**：
   - 前置条件（需要登录、需要什么角色）；
   - 复现步骤（A 的请求改成 B 的 ID）；
   - 实际影响（读取/修改他人订单、提权、金额损失）；
   - 修复建议（对象级鉴权、字段白名单、服务端计价）。
